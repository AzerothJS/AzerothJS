# azerothjs / i18n

[![npm](https://img.shields.io/npm/v/azerothjs?color=2ea44f)](https://www.npmjs.com/package/azerothjs)

Part of [AzerothJS](https://github.com/AzerothJS/AzerothJS) - the fine-grained fullstack framework. Applications usually install [`azerothjs`](https://www.npmjs.com/package/azerothjs); depend on this package directly for a narrower surface.

## Overview

Publishing a site in more than one language is three separate jobs: deciding which language a
reader gets, saying so in the document, and writing the strings. The framework owns the first
two, because they depend on the request and on the document, and gives you the third as ordinary
TypeScript.

```ts
// server entry
mountPages(app, {
    routes,
    clientDir: 'dist',
    renderer,
    locales: { supported: ['en', 'fa'] }
});
```

That one line is the whole setup. Every request is negotiated, and every page is served with its
own `<html lang>` and `<html dir>` already correct - before any JavaScript runs, which is what a
crawler and a screen reader both need.

## Install

```sh
npm install azerothjs
```

## Which language a reader gets

In order:

1. **Their own choice**, from the `locale` cookie that `setLocale()` writes.
2. **`Accept-Language`**, read in *preference order*.
3. **The default**, which is `supported[0]` unless you name one.

The preference-order part is worth stating, because it is the half that hand-rolled detectors get
wrong. A reader whose header is `en-US,fa;q=0.9` has asked for English and would *accept* Persian.
Scanning the header for "is Persian in there" answers them in Persian, which is exactly backwards.

A regional request is served by the language it belongs to, so `fa-IR` and `fa-AF` are both served
by a `fa` catalogue, and a site that publishes `zh-CN` can answer a bare `zh`.

The cookie is resolved against your supported list rather than trusted - it is reader-supplied
text, and it would otherwise reach the document element.

## In a component

```ts
import { useLocale, useDirection, setLocale } from 'azerothjs';

const locale = useLocale();          // () => 'fa'
const dir = useDirection();          // () => 'rtl'

setLocale('fa');                     // switches the page and remembers it
```

`useLocale()` is reactive, and that is the design rather than a detail. Everything derived from it
re-runs when it changes, so switching languages reformats a date without the component knowing it
held a date, and the page never reloads.

`setLocale()` writes the choice to a cookie, so the *next* request is rendered in that language on
the server rather than corrected after it arrives. Pass `{ cookie: false }` to switch without
remembering.

## Messages

A catalogue is a plain object. The first one is the reference: its keys become the type, so a
translation that forgets a key or invents one is a build error.

```ts
import { createMessages } from 'azerothjs';

export const t = createMessages({
    en: {
        'cart.empty': 'Your cart is empty',
        'cart.items': { one: '{count} item', other: '{count} items' }
    },
    fa: {
        'cart.empty': 'سبد خرید شما خالی است',
        'cart.items': { other: '{count} مورد' }
    }
});

t('cart.empty');
t('cart.items', { count: 3 });
```

Placeholders are `{name}`. One you do not supply is left as written rather than blanked, so the
mistake is visible instead of silent.

A key missing from the reader's language falls back to the reference language: a page in the wrong
language is readable, a page of empty strings is not. A key missing from *every* catalogue renders
as itself and says so once, in development.

### Plurals are the language's business, not yours

`count === 1 ? one : other` is correct for English and wrong for most of the world. Arabic
distinguishes six forms and Russian four, so pass a `count` and let the framework ask `Intl`:

```ts
const t = createMessages({
    en: { files: { one: '{count} file', other: '{count} files' } },
    ru: { files: { one: '{count} файл', few: '{count} файла', many: '{count} файлов', other: '{count} файла' } }
});

t('files', { count: 3 });   // ru: "3 файла"
t('files', { count: 7 });   // ru: "7 файлов"   <- a one-or-other rule gets this wrong
```

Write only the forms your language uses; anything unspelled falls back to `other`.

## Numbers, dates and elapsed time

```ts
const n = useNumberFormat();
const d = useDateFormat();
const ago = useRelativeTimeFormat();
const list = useListFormat();

n(1234567.89);                              // 1,234,567.89   /   ۱٬۲۳۴٬۵۶۷٫۸۹
d(post.publishedAt, { dateStyle: 'long' }); // Persian gets the Jalali calendar
ago(comment.createdAt);                     // "3 days ago"
list(['Ada', 'Grace']);                     // "Ada and Grace"
```

All four follow the locale signal, so they redraw on a switch.

**None of this is applied automatically, deliberately.** A localized digit is right in a sentence
and wrong in an identifier, a price in a form field, an account number, or anything a machine
reads back. These are functions you choose per call site, never an ambient transformation.

## Every render mode

| mode | how the language is decided |
| --- | --- |
| `'server'` | negotiated per request; the render is pinned to it |
| `'stream'` | the same, pinned for the whole response - a Suspense boundary that settles later still answers in the reader's language |
| `'client'` | the shell is stamped before it is sent, so the page is labelled correctly before any script runs |
| `'static'` | the build writes one file per language; the mount serves the reader's own |
| ISR | the language is part of the cache key, so one reader's language is never served to the next |

For a static build, pass the same list to the prerender pass:

```ts
await prerender({ routes, clientDir: 'dist', renderer, locales: ['en', 'fa'] });
```

That writes `about/index.en.html` and `about/index.fa.html` beside `about/index.html`. The
unsuffixed file is still written, so a host that does no negotiation still has a page to serve.

Responses that were negotiated carry `Vary: accept-language`, and `cookie` as well when the
reader's own choice decided it - named per response rather than always, because naming `Cookie`
unconditionally would make every page uncacheable for the sake of readers who never chose one.

## Outside a page

Anything holding a `Request` can ask the same question, with the same rule:

```ts
import { negotiateLocale } from 'azerothjs';

app.get('/events', (context) => {
    const { locale } = negotiateLocale(context.request, { supported: ['en', 'fa'] });
    return sse(context.request, (send) => send({ data: greeting(locale) }));
});
```

Use it for SSE streams, JSON endpoints, and anywhere a response carries text but no document. One
implementation, so a site's API cannot answer in a different language from its pages.

## Direction

`dir` is set from the language by `Intl`, not from a table this framework maintains - so Central
Kurdish, Sindhi and Yiddish are right without anyone remembering them.

Write your CSS in logical properties (`margin-inline-start`, `border-inline-start`,
`padding-inline`) and a right-to-left page lays itself out correctly with no other work. Reach for
`useDirection()` only where a component genuinely has to branch.
