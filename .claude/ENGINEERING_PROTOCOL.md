# AzerothJS engineering protocol

This is the shared contract for engineers working through Codex, Claude Code, or another client. The maintainer sets scope and product policy. The principal engineer owns the technical decision, verification, integration and handoff within that scope.

## Start or resume

1. Read this file and [the handoff](ENGINEERING_STATE.md). Open the original `.claude/ROADMAP.md` and `.claude/framework-bugs.md` in this checkout. Read the roadmap invariants, current execution order and relevant ledger entries. Locate the affected bug, its history and linked decisions. Use section searches and bounded reads for these large files. When either original is missing, record which one and request the maintainer's copy before making a decision that depends on it.
2. Follow [the architecture index](ARCHITECTURE_INDEX.md) to the relevant design record, current implementation, callers, package exports and tests. For a roadmap milestone also read `.claude/skills/azeroth-production-roadmap/SKILL.md` and use its design, positive-control, real-app and completion matrix. Verify historical claims against the current revision.
3. Inspect `git status --short --branch --untracked-files=all`, the staged and unstaged diffs, and the relevant history. Identify pre-existing work, ownership and overlaps. Record the baseline and a task identifier. Use a descriptive identifier for engineering work without a product entry. See the handoff before staging either original canonical file for the first time.
4. Define observable acceptance criteria, affected boundaries and verification commands. Reuse an existing implementation wherever it satisfies the requirement. Record unknowns and the evidence needed to resolve them.

## Lifecycle for a logical change

| Stage | Evidence required to proceed |
| --- | --- |
| Discovery | A trace from the real entry point to the affected behavior, with paths, existing abstractions and the applicable product contract. |
| Baseline | Run the relevant existing checks before editing. Record revision, environment, build/typecheck/test status, and browser or console findings when applicable. Separate pre-existing failures from changes introduced here. |
| Root cause | For functional defects, capture the original failure with a deterministic regression case when possible. Trace initial state, first incorrect operation, violated invariant, affected paths and observable consequence. If a pre-fix run is unavailable, record why and what alternative evidence supports the diagnosis. Route security findings to defensive review. |
| Independent proposals and refutation | For substantial work, obtain independent design analysis. Compare options for ownership, concurrency, compatibility, complexity, performance and security. Have a separate reviewer challenge the preferred option with concrete counterexamples. Resolve disagreements against source or a discriminating test. Scale mechanical work to its actual risk. |
| Decision | Before implementation, record cause, chosen approach, rejected alternatives and reasons, impacted files/APIs, acceptance criteria, test plan and residual risks. Use the handoff for a small decision or the relevant existing design dossier for a durable one. A significant new decision without an existing dossier may use `.claude/decisions/<topic>.md`. |
| Implementation | Give one owner a named set of files and a contract. Coordinate test and documentation ownership. Ship related tests with the implementation. Reassess when the evidence contradicts the design or the patch changes the contract. |
| Independent testing | A second perspective checks the actual entry points and whether assertions can fail. Exercise the original functional defect before and after the correction where feasible. Select the applicable layers below. |
| Independent review | Give a different reviewer the actual diff, tests, decision and acceptance criteria. Resolve critical and high findings before acceptance. Revisit architectural refutation if the implementation changes a material assumption. |
| Final verification | After the last correction, rerun the affected checks, review the final diff and compare observed outcomes with the acceptance criteria. Report remaining uncertainty. |
| Documentation and Git | Update the original roadmap and bug entries when their verified status changes. Preserve prior evidence and link related entries. Record newly confirmed functional issues in the existing tracker. Handle sensitive findings under `SECURITY.md`. Update the handoff, then verify and commit each logical change as below. |

A passing assertion alone cannot justify a change to a public contract. Check sibling paths, malformed and boundary values, repeated calls, concurrency, cancellation, teardown, recovery and backwards compatibility where applicable. Fix the invariant at its owner. Reject swallowed errors, disabled assertions, unbounded retries, timing sleeps, duplicate fallbacks, speculative APIs and unrelated refactors.

## Delegation and access

Choose roles from [agent-specs](agent-specs/) according to the work. Give each agent the task ID, relevant paths, expected output, exact write scope and available evidence. Parallelize independent reads and disjoint writes. Serialize work on a shared module, tracker, index or handoff. The principal engineer inspects the evidence and owns staging and commits. Reviewers return findings without editing the work they review.

The shared role file defines each assignment. A native tool allowlist or parent sandbox may further restrict it. Codex custom agents inherit parent permissions and MCP servers. Its read-only instructions are an operating boundary. Use a parent with read-only filesystem access and appropriate external tool permissions when enforcement is required. Claude read-only roles use file-reading tools. The principal supplies the exact Git diff, history or command output when a role lacks shell access. The principal or test owner starts local fixtures for browser QA.

## Verification

- Inspect root and affected workspace manifests before choosing commands. The root `npm run verify` builds the workspaces, lints, typechecks, validates package metadata and runs Vitest. Use `npm run smoke` after building when packed consumer behavior matters. Exercise selected tests through `npm test -- <spec-path>`. See `vitest.config.ts` for environment and build prerequisites.
- Unit tests exercise isolated behavior. Integration tests exercise the real compiler/runtime, request pipeline or package boundary. Check package exports, supported runtimes and published types for compatibility changes. Use harmless inert markers and expected encoding or rejection assertions for defensive security checks.
- For browser-facing work, independent `playwright-qa` must use an actual Playwright MCP connection after the final change. Verify tool discovery, launch and navigate to the affected route in an isolated test context. Inspect the accessibility tree and DOM-visible result, use real controls, and check loading, empty, error, success and cleanup behavior as relevant. Inspect console errors, uncaught errors and failed requests. Run relevant supported engines for critical browser behavior. A screenshot alone does not establish behavior.
- For SSR, compare server output, initial browser content, hydration and subsequent client updates. Exercise relevant nesting, arrays, branches, Suspense, streaming, malformed input, repeated renders and the distinction between text and trusted markup. Use inert inputs to assert text and DOM structure. For repeatable browser contracts add deterministic, isolated Playwright Test cases in the established test layout, establishing a justified test harness when needed. Keep direct MCP and automated regression results distinct.
- Prefer loopback apps and local fixtures. Use a clean browser context without production credentials, cookies or storage. Avoid unrelated destinations, real payments, production data and destructive transactions. Keep browser profiles, secret-bearing screenshots, auth state and environment values out of Git. MCP is a tool connection and does not enforce application authorization. Use ordinary browser tools for verification.
- Record the exact environment, command or MCP tools invoked, engine, scenario, expected and observed results, errors, failed requests, limitations and verdict. Report **passed**, **failed**, **blocked**, **not applicable**, or **not executed** per layer. An absent MCP blocks browser acceptance. Pure Node, build and type-only work uses native checks. Document the reason if there is no meaningful browser surface.

## Git and shared state

Keep each independent change in its own verified commit. After independent review, inspect `git diff`, stage exact owned paths, and inspect the full `git diff --cached` and file list. A regular commit includes all staged paths. If unrelated changes are already staged, isolate the planned commit, verify its complete contents independently, and preserve the user's staging exactly. For an overlap, select only separable task-owned changes. If separation is unsafe, leave the index and the user's work intact and report the conflict. Preserve staged, unstaged, untracked and ignored user work. Avoid broad staging, cleanup, resets and restoration of user files.

Commit automatically after verification using the configured local author and a single Conventional Commit subject describing the change. Omit attribution and co-author trailers. After each commit inspect `git show -s --format=fuller HEAD`, `git show --format= --name-status HEAD` and `git status --short --branch --untracked-files=all`. Check the full message, author and file scope. Report unexpected hook attribution. Pushing, force-pushing, rebasing user commits, amending, tagging or rewriting history needs separate explicit direction.

This standing authorization governs ordinary verified work. Older local instructions in the roadmap and historical commands describe earlier commit arrangements. Preserve their technical gates and command tool restrictions. A restricted command returns its work to the principal for review and commit. A current user instruction to leave work uncommitted takes precedence.

Keep [ENGINEERING_STATE.md](ENGINEERING_STATE.md) small enough to resume from a fresh chat. After each meaningful milestone or provider transfer, record focus, active ID or idle status, decision, file ownership and progress, commit references, executed checks and results, outstanding risks/blockers, and one exact next action. Use Git to resolve the handoff commit's own hash. Update canonical product records in place. On changes to this protocol or the role set, inspect **both** entrypoints, provider adapters and effective permissions, then check a fresh provider session.
