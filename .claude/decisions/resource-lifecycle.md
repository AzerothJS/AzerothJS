# Resource keys, refresh and settlement

Unit 7 covers A-162, A-198, A-209, A-312 and A-317. Base revision `18c3238`. The consumer reports are entries 35 and 48. The latest fetcher tracking and optimistic cache decisions apply. This design leaves future streamed seed holds to A-288.

## Observed failures

At the public API, two writes behind an unchanged plain key produced three starts and two aborts. A cached control produced one start. A compiled Suspense editor lost its input. Stream cancellation removed the source subscription, so the next question never started. A superseded island request could resolve a refetch caller with the old value, or keep it waiting indefinitely after the winning value arrived. A construction-batch refetch could be absorbed by a seed. A batched shared refetch could force the abandoned key. A stream parser could also append the last buffered record of an aborted reader to the next stream.

## Decision

- A sourced resource or stream has one internal memo for the logical key. Create it on the first driving run under the construction owner and preserve the driving error handler. This preserves deferred construction in a batch and string-mode behavior. Read the source once per computation. Compare usable keys with `Object.is` or a typed `equals(previous, next)` option. Retain the accepted representative across equal evaluations. The skip values are `false`, `null` and `undefined`. Bypass application comparison across skips and failures. A comparator runs untracked. Represent a thrown value from either callback as a distinct memo outcome and throw the original from the driver, so its existing error handler sees it and recovery can run. An explicit refetch resamples even a nonreactive source. Plain string rendering and eager SSR streaming keep their prior entry points.
- The drive observes the key and the explicit command. Equal-key notifications leave the current request, owner cleanups, Suspense input and stream intact. Explicit demand resamples the level source, which stages the current loader descriptor before fetch. The router keeps its synchronous single-slot handoff when caching is disabled and its weak cache-entry registry when enabled.
- Plain resources distinguish a successful value for the current key from a cold load, including a success whose value was `undefined`. A same-key refetch retains a successful value, sets `refreshing()` and keeps Suspense children mounted. A genuinely different key starts cold and clears the previous key's data. Skip clears both flags and data. A failed warm refresh retains its last success and publishes the error. A failed first read remains cold on retry. A valid seed counts as a success, a failure seed as an error. The shared path keeps its cache-entry display rules.
- Each live instance records refetch demand before waking its driver. A batch selects its final key once. Several calls in one batch can share a fetch. A new explicit call outside a batch still supersedes the prior fetch synchronously. Pending callers follow the live instance to its current key. They resolve at the first authoritative settlement that covers their request or an already available result on the new key. An obsolete raw promise cannot release or hold a caller. Success and failure both release eligible callers after publication, including when a subscriber throws. A new demand raised by a settle observer belongs to the next generation. Skip, source failure and disposal release abandoned demand. String rendering has no live refetch driver.
- A shared fetch still goes through the cache's force and settlement machinery, including replacement caused by a mutation. The driver applies a forced read to the final bound entry and registers an instance settlement observer that can detach when it changes keys or disposes. Cache bookkeeping remains authoritative for marks, post-write generations and settlement. A seed is still adopted on first drive. Explicit demand in the construction batch also starts one authoritative read after adoption and joins its settlement. An unseeded resource in that batch makes one request.
- Stream cancellation aborts and marks done while continuing to observe the accepted key. Equal keys stay idle after cancel. A different usable key or a later explicit refetch starts again. An active cancellation wins when batched with refetch or a key change, as on the baseline. A superseded reader cannot flush its buffered parser tail into the next stream. Recheck cancellation after an application parser runs because it can synchronously replace the stream before returning its parsed text. Current-stream final flushing, skip reset and string rendering are preserved.

Untracking the entire effect loses its inputs. Moving the comparison into the existing effect body still runs its previous cleanup on an equal key. An eager construction-time memo reads too early during batching and server rendering. A raw memo that swallows a handled source exception can return the old key. Chaining superseded fetch promises cannot release a caller if an old fetch ignores cancellation. A per-depth router registry was proposed for a drive that could force an unsampled memo. Removing it from the final design passed nested navigation and batched explicit refetches because this drive resamples its key. An unbounded map of triggers would also extend their lifetime past their entries. The design reuses the existing graph, AbortControllers, cache and effect error routing.

## Compatibility and verification

### Refutation addendum

A source getter can dispose its own component before it returns the next key. On the base revision and initial candidate, the abandoned resource and stream still started a request. A cached resource also retained a subscriber after disposal. Check the instance lifetime immediately after evaluating the key and before acquiring an entry or starting a request. The owning cleanup already releases pending refetch callers. If that callback throws after disposal, route its original error through the captured handler. Apply this at the two framework-owned drivers, including their first drive. A general change to effect scheduling cannot interrupt an application callback that is already executing.

### Release behavior

The new comparator is optional and passes through the existing keyword options. A mutated object with stable identity and an unchanged failed key need an explicit refetch to retry. Plain-resource warm refreshes preserve child state. On a different key, consumers see a cold load or the shared entry for that key. The resource's promise represents observable settlement. These public behavioral changes require release planning under [VERSIONING.md](../../VERSIONING.md). There is no new request authority, package, wire format or emitted runtime helper.

Run source and cached controls with a deferred fetch that honors or ignores abort, batched key and force changes, reentrant settlement, skip, owner disposal, source failure and recovery, seeds and stale cache updates. Verify both suspended and retained DOM, nested loader staging, real-key stream restart, aborted and active final chunks, SSR and hydration. Break the significant seams independently and run the matching assertions. Check compiler and editor support for the comparator, ordinary package prepack artifacts, the published build, independent Playwright QA and the full repository gate.

The release keeps the existing public entry points and requires the migration described above for consumers relying on the old refresh or retry behavior. Separate follow-ups include A-327's seed/mark precedence, A-288's streamed seed identity, and the first-run effect registration case described below.

If a source disposes an **ancestor** while an outer effect is still in its own initial execution, the outer effect may not yet have registered its disposer with that ancestor. The first inner request can start and is then aborted during registration. This reproduced on the base revision and final tree for plain resources, shared resources and streams. The shared entry ended with zero subscribers. The scheduler's first-run registration order needs its own ownership decision and regression controls.
