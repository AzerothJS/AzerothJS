# Locale ownership across the build and server

## Unit 13 · A-18, A-46, A-66 and A-186

At `f866b51` the prerender binary reads only the routes and renderer from the application's SSR entry. A multilingual mount can negotiate Persian but find only the unsuffixed file from that build. Both the literal route handler and the enumerated static handler prefer that file to rendering in the requested language. In a separate single-language case Kit keeps the Persian shell's HTML attributes but renders English content because the component render has no pinned locale. The browser seeds its language from the actual document element.

## Contract

- The SSR entry is the shared configuration boundary. It may export `locales` (the mount's complete language configuration) and `origin` (the canonical public HTTP or HTTPS origin for alternate links). The prerender bin and development entry loader read these fields. The production scaffold passes them to the mount beside its routes and renderer. An older entry still works. Development accepts the existing mount options when the entry omits the field. Existing custom production hosts can forward the optional exports. Public origin validation runs before writing files or mounting routes.
- A multilingual build writes a suffixed file for every supported language. Its unsuffixed document uses the same resolved default as negotiation. The filename and URL base are distinct from the render language. Under prefix routing the unsuffixed file belongs to the bare URL, while a suffixed file carries the language prefix. Keep the existing programmatic list of locales and routing option. An unconfigured build preserves the established layout and shell bytes. Preserve rollback across failed builds.
- Use the existing alternate-link builder. Under prefix routing a configured origin applies to prerendered, live and regenerated links. Without it, shared and static output keep root-relative links and live pages use the request origin. The build and mount hash the shell together with the normalized origin and effective ordered prefixes. Switching to prefix routing, adding a prefix or changing the canonical origin invalidates a persistent ISR copy even when the client shell is identical. The origin-free, prefix-free hash stays compatible with older deployments.
- A negotiated static file hit keeps the file server's validators and representation. A missing translation with a renderer goes through the ordinary request render, including the negotiated locale, request, abort signal and Vary policy. Without a renderer, serve the existing unsuffixed artifact and report that fallback through `onError`, at most once per declared route pattern and supported language per mount. Arbitrary slugs do not grow the notice set. A prefix miss keeps its live-render or shell behavior. Existing guard checks, prefix stamp failures, rendererless status codes, and ISR seed selection keep their own owners.
- Without explicit locale configuration the renderer reads the language of the shell's opening document element and binds it while generating component content. Do this for buffered output and each streamed boundary, preserving the actual shell attributes. Missing or empty language uses the normal English fallback. An explicit locale still owns stamping. Read the real attribute token, including normal quoting and escaped language characters, without mistaking comments or quoted strings for markup. The document element reader also identifies the existing prefix stamp. It must work without third-party runtime packages.

## Alternatives and acceptance

A CLI flag would leave the documented build without a source for the mount configuration. Copying locale resolution into the CLI would let its default disagree with runtime negotiation. Stamping the unsuffixed file with a prefix would make the browser adopt the wrong base. Relabeling a fallback file cannot translate its content. Changing a process-global language across an asynchronous render would mix simultaneous requests. Keep this work in Kit and the scaffold, with the existing v6 component compiler/runtime contract.

Compare real build artifacts, status, document language, direction, rendered text, client hydration and interaction. Exercise header and cookie negotiation, translated and missing files, per-file ETags, no-renderer notices, custom public origin, prefix redirects and hreflang, ISR seeds and regeneration, and a single-language Persian shell. Check existing entries and programmatic callers. Prove regressions against the baseline and faulty variants, then run independent packed browser verification, review, the repository gate and clean-consumer package smoke.

## Review and deployment

The initial design invalidated persisted pages only when the shell or origin changed. The reviewer traced how the same route and locale cache key survives a switch from negotiated to prefixed routing. Reusing that page would boot the client from a document with the wrong base. Changing the set or order of prefixes also changes its alternate links. Both the producer and consumer now include these inputs in deployment identity.

The refuter also identified repeated artifact writes during rollback. Restoring them in reverse order returns each file to its pre-build contents even when two routes name the same output. A configuration that lists two tags differing only by case is rejected before writing or mounting because their filenames alias on common filesystems. When accepting a custom renderer's document, the effective first base attribute must contain a value. A later duplicate cannot supply the stamp the browser reads.

Use the same SSR entry and matching assets throughout a deployment. Existing custom servers can forward its optional exports to `mountPages`. An existing build with missing language files can recover per request with a renderer, but a plain static host needs rebuilt artifacts to serve each language. Shell-language inference handles an explicit document element in a standard HTML prologue. The existing mount reads the first 4 KiB to verify a prefixed file's stamp. The component compiler and its v6 output format are unchanged.
