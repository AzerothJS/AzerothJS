# Streamed resource seed ownership

## Revision 2 for A-288

At `b87d15f` the server gives each resource an ordinal as it serializes. The browser constructs eager siblings before walking lazy branches. A boundary can therefore adopt another widget's value, even when both values have the right type. Reordering construction cannot solve reverse-order hydration of two roots. The boundary that awaited the resource already has both pieces of its address, its document ID and the resource's index in the full `Suspense.on` list.

Use `N.i` in the seed store. Capture the ordered list at boundary construction. Only resources with an actual server fetch contribute values. Two boundaries sharing a resource may each carry its outcome. A boundary whose resources already settled in a continuation uses the same numbered marker as a pending one. Its enclosing chunk carries its addressed group. Serialize the chunk before scheduling nested boundaries. A serialization failure reports the error, discards that chunk and its descendants, and leaves the fallback available for client recovery.

Each synchronous hydration window can hold the initial fetch when a boundary seed is available. Within this window, a boundary hands each outcome to the resource at the same index. Remaining resources start through their own effect on successful exit. A failed window discards its holds. A seed can replace a released initial request during a later adoption only while the same request and source are current. Explicit refetch, source change, cache invalidation, newer data and disposal take precedence. A skipped source, options seed or loader view keeps its existing behavior. A cached outcome uses its existing entry and preserves the cache's ownership of a shared request. Seed application and release do not advance the public refetch generation. Adopted DOM observers see publications in DOM mode.

The swap script records delivery in a new weak set. Its legacy delivery set stays empty, so an older JS bundle takes its fallback before evaluating typed children with missing data. The new client recovers incomplete or superseded ready data by rebuilding that boundary's range with the existing Show driver. Its owning resource, explicit request and siblings survive. Development diagnostics identify detectable list-length or name mismatches. Abandoned-marker diagnostics inspect completed root ranges and account for deferred routes and islands. Production adds no diagnostic fields. All wire data uses the existing inert JSON serializer.

The template identifies the already-settled inline descendants it delivers. The swap records their actual comment nodes, so a missing child seed can trigger local recovery even when the entire group is absent. A pending sibling still adopts its fallback. Replacing a range, root or island retires the groups belonging to its removed markers. Duplicate or incomplete swap calls preserve the current DOM.

An empty seed store allows the first fetch to start at its ordinary time. An eligible pending request can still receive a chunk delivered before a later root adopts the boundary. A cache seed publishes through the shared entry in the adoption batch so a subsequent invalidation has the usual precedence, including when the resource's first effect is queued. Capturing the watch list also resolves A-322 for state-dependent getters and arrays edited after construction.

This choice replaces resource counters on both sides. It preserves the public resource and Suspense APIs, compiler v5 output and the existing loader handoff. A setup read of an awaited resource can now see its initial loading state, as on the server. A resource outside an adopted boundary fetches on the client. Tests must distinguish real seed adoption from a matching-looking client refetch, including reverse roots, cache reuse, pending and settled nested boundaries, late or stale results and rollback. Separate stream sessions sharing one document remain A-320.

The latter alternatives depend on the order in which the client visits independently hydrated roots. Holding all initial requests until the end of hydration also delays buffered work and can lose the fetcher's owner on release. The implementation uses the existing resource effect, cache entry and Show driver for those operations.

## Cost and limits

With 100 streamed boundaries, 23 warmed server samples from each production package gave median full-response times of 0.87 ms before and 1.17 ms after. Uncompressed HTML increased from 28,882 to 31,148 bytes. A two-boundary response grew from 3,360 to 5,528 bytes, largely from the once-per-response swap runtime. For 100 correctly ordered rows, Chromium's median synchronous client bootstrap went from 2.8 ms (interquartile range 2.6–3.2) to 3.3 ms (3.0–3.6) over 21 alternating measured runs per package. Each pack received five warmups. Every run adopted all 100 original nodes without client fetching. These local timings exclude network and paint.

Keep the same ordered watch list on both sides. Length and available names catch some disagreements in development. Reordered indistinguishable resources remain an application contract. The historical prototype and audit lanes are outside this checkout. This verification uses current compiler output, the current resource lifecycle and fresh packed applications.
