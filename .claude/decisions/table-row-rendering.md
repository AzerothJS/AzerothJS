# Compiling bare table rows

## A-145

At `9305d00`, the static template contains `<table><tr>`, and the compiler calculates binding paths as though the row were the table's first child. The browser's template parser places a `tbody` there. A cell binding can consequently clear the row or miss its target entirely. The packed inventory page failed in Chromium on both the default build and the client-only build. An explicit `tbody` worked. The same browser could adopt and update both pages from served HTML.

## Decision

Lower statically known row groups of an HTML table to `tbody` elements in the shared render plan. Row contents can have arbitrary bindings. Keep explicit sections and their attributes, preserve HTML table whitespace, and keep nested tables independent. Use the existing plan IDs for bindings. The clone string, binding paths, server output, adoption descriptors and eager construction all derive from this structure. This applies to embedded markup and render callbacks as well as a top-level component.

A direct expression or component can return a row on one write and a table section on the next. For a table mixing a bare row with unresolved siblings, preserve its server output and adoption rules. For the fresh clone, materialize each known group up to the next unknown child. Keep each unknown child's anchors on the table so its value can become a footer. Column groups and script-supporting elements follow the HTML parser's placement. Foster-parented static literals need an isolated parsing context in the clone so their offsets cannot displace later bindings. Only compiler-created placeholders may be opened. Reuse this layout for both the serialized clone and its paths, including render callbacks.

Fixed rows keep their native body in a clone. An eager expression and a hydrated mixed table retain their previous logical child descriptors. A projected row can be a child of `table` on a fresh mount and share an implied `tbody` on adoption. Explicit sections give authors control over both parents. The earlier candidate built an entire mixed render plan eagerly. Independent Chromium checks showed it lost an unrelated native template's contents and an input's reset defaults. Keep native cloning for those subtrees. A-141 covers the existing hydration limitations as projected children change shape.

A blanket diagnostic would break working server and hydrated applications. Adjusting only the generated index leaves the anchor parent unresolved and makes the output depend on the parser. Wrapping a mixed range unconditionally can put a `tfoot` in a `tbody`, or split a reactive range's two anchors across different parents. Independent design and refutation traced these cases through the existing route outlet and branch suites.

This uses compiler/runtime contract 7 and the existing renderer, escaping, signal ownership and teardown. Rebuild the application and any precompiled components to obtain the corrected paths. The repository adds Playwright Core as a development dependency for the permanent Chromium regressions. Published packages gain no dependency.

## Acceptance

Compare the same compiled table with bare rows and an explicit `tbody`. Inspect actual row and cell parents, update a reactive cell, and retain the same cell and pretyped input after adoption. Check consecutive rows, section boundaries, transparent markup, nested tables, row callbacks and a child that changes between a row and a section. Exercise default cloning and `ssr: false`, served buffered and streamed HTML, hydration, and the existing range and route suites. Run the packed app on Chromium, Firefox and WebKit and repeat the affected workflows through registered Playwright MCP.

## Results

- The packed baseline reproduced 60 failed client starts and forced fallbacks. Twelve new conformance cases gave six failures and six passing controls on `9305d00`. All twelve pass on the correction.
- The permanent Chromium test compiles the native parser cases through Vite under both targets. Eight of the twelve scenarios failed on the baseline. All four positive controls passed there. All twelve pass on the accepted change, including column groups, form reset defaults, inert template contents, folded text and a table inside a render callback. Run `npm run test:browser:tables` after building and installing the Chromium binary.
- Independent investigation executed the 16 historical route layouts in Chromium. Fifteen fresh mounts threw on the baseline, and the last placed the page after the layout footer. The corrected clone mounted all 16 and retained their historical hydration traces through all seven updates and navigations. The route suite now reads the live DOM in both lanes. Reparsing a live table for inspection had inserted an extra row group in nine cases.
- The packed inventory app built 27 times. All nine pages produced identical buffered and streamed markup. The final compiler produced byte-identical bundles and served documents to the reviewed candidate across all 45 build outputs and 54 request routes. Chromium, Firefox and WebKit exercised development and production builds. All 216 table checks passed, and all 168 interactive cases kept the original draft and nodes through their updates. The native receipt passed 24 additional checks. Registered Playwright MCP passed nine workflows, observed 148 HTTP 200 responses, and saw only the warning from the deliberate mismatch.
- A receipt with a populated native HTML template also exposed a pre-existing hydration mismatch on six normal dev/production loads. A standalone packed page on `9305d00` reproduced the neighboring input loss with no table present. The renderer starts its cursor on the template element, while the browser stores those children in its content fragment. A `section` control retained the input. A-341 and tracker entry 57 record this separate defect.
- On Windows with Node 24.22.3 and npm 11.18.0, full verification passed 8,178 tests in 465 files with two skipped. Smoke installed all 15 packed workspaces. An earlier overlapping run briefly removed the built WebSocket entry while an HTTP integration test needed it. The complete verification rerun passed with the gates running separately.
